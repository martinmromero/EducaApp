Fundamentos de Bases de Datos Relacionales

Introducción

Una base de datos relacional organiza la información en tablas compuestas por filas y columnas,
donde cada fila representa un registro y cada columna un atributo de ese registro. El modelo
relacional, propuesto por Edgar F. Codd en 1970, se basa en la teoría de conjuntos y la lógica de
predicados, y sigue siendo hoy la base de la gran mayoría de los sistemas de gestión de bases de
datos utilizados en la industria, como PostgreSQL, MySQL, SQL Server y Oracle.

Cada tabla de una base de datos relacional debe tener una clave primaria: un campo (o combinación
de campos) que identifica de forma única a cada fila. Ninguna fila puede repetir el valor de la
clave primaria, y ese valor no puede ser nulo. Cuando una tabla necesita referenciar filas de otra
tabla, se utiliza una clave foránea: un campo cuyo valor debe coincidir con el de una clave primaria
en la tabla referenciada. Este mecanismo es lo que garantiza la integridad referencial del modelo:
no puede existir, por ejemplo, un pedido que referencie a un cliente inexistente.

Normalización

La normalización es el proceso de organizar las columnas y tablas de una base de datos para
minimizar la redundancia de datos y evitar anomalías de inserción, actualización y borrado. Existen
varias formas normales, cada una más estricta que la anterior.

La primera forma normal (1FN) exige que cada columna contenga valores atómicos, es decir, que no
haya listas ni conjuntos de valores dentro de una misma celda, y que no existan grupos de columnas
repetidas. Por ejemplo, una tabla de clientes no debería tener una columna "teléfonos" con varios
números separados por comas; en su lugar, debería existir una tabla aparte de teléfonos vinculada
al cliente mediante una clave foránea.

La segunda forma normal (2FN) requiere que la tabla esté en 1FN y que todos los atributos no clave
dependan de la totalidad de la clave primaria, no solo de una parte de ella. Este problema aparece
sobre todo en tablas con claves primarias compuestas: si un atributo depende únicamente de una parte
de la clave compuesta, se dice que hay una dependencia parcial, y esa dependencia parcial debe
eliminarse trasladando el atributo a una tabla separada.

La tercera forma normal (3FN) exige que la tabla esté en 2FN y que no existan dependencias
transitivas, es decir, que ningún atributo no clave dependa de otro atributo no clave en lugar de
depender directamente de la clave primaria. Un ejemplo clásico es una tabla de pedidos que incluya
tanto el código postal del cliente como la ciudad correspondiente a ese código postal: la ciudad
depende del código postal, no directamente del pedido, así que debería normalizarse en una tabla de
códigos postales separada.

Si bien normalizar reduce la redundancia y previene inconsistencias, un exceso de normalización
puede complicar las consultas al requerir muchos joins entre tablas, lo que en sistemas con alta
carga de lectura puede afectar el rendimiento. Por esa razón, en ciertos escenarios de análisis de
datos o reportes se aplica el proceso inverso, llamado desnormalización, que consiste en introducir
cierta redundancia controlada para mejorar el desempeño de las consultas más frecuentes.

Consultas SQL

El lenguaje SQL (Structured Query Language) es el estándar utilizado para definir, manipular y
consultar datos en un sistema relacional. Se divide habitualmente en varios subconjuntos: DDL
(Data Definition Language) para crear y modificar la estructura de las tablas, DML (Data
Manipulation Language) para insertar, actualizar y borrar datos, y DQL (Data Query Language),
centrado en la instrucción SELECT, para consultar datos.

Una consulta SELECT básica indica qué columnas se quieren obtener y de qué tabla, y puede filtrarse
con la cláusula WHERE, que evalúa una condición fila por fila antes de que existan agrupamientos.
Cuando se necesita agrupar filas y calcular funciones de agregación como COUNT, SUM, AVG, MIN o MAX,
se utiliza la cláusula GROUP BY, y si además se necesita filtrar los grupos resultantes según una
condición sobre esas funciones de agregación, se utiliza la cláusula HAVING, que a diferencia de
WHERE se evalúa después de agrupar.

Los JOIN son la herramienta central para combinar información de varias tablas relacionadas. Un
INNER JOIN devuelve únicamente las filas que tienen coincidencia en ambas tablas. Un LEFT JOIN
devuelve todas las filas de la tabla de la izquierda, y las columnas de la tabla de la derecha
aparecen como nulas cuando no hay coincidencia. Un RIGHT JOIN es el caso simétrico, y un FULL OUTER
JOIN devuelve todas las filas de ambas tablas, coincidan o no. Elegir el tipo de JOIN correcto es
crucial: usar un INNER JOIN cuando en realidad se necesitan también las filas sin coincidencia es
un error frecuente que produce resultados incompletos sin que salte ningún error.

Índices y rendimiento

Un índice es una estructura de datos auxiliar, generalmente un árbol balanceado (B-tree), que
permite localizar filas rápidamente sin tener que recorrer la tabla completa. Los índices aceleran
notablemente las consultas de lectura que filtran u ordenan por la columna indexada, pero tienen un
costo: cada operación de inserción, actualización o borrado debe también actualizar los índices
asociados, lo que hace más lentas las escrituras. Por eso, indexar en exceso columnas que rara vez
se consultan, o que cambian muy seguido, puede ser contraproducente.

La clave primaria de una tabla suele tener un índice creado automáticamente por el motor de base de
datos. Para el resto de las columnas, la decisión de indexar depende del patrón de consultas: como
regla general, conviene indexar las columnas que se usan con frecuencia en cláusulas WHERE, en
condiciones de JOIN, o en ORDER BY sobre tablas grandes.

Transacciones y propiedades ACID

Una transacción es una secuencia de una o más operaciones que se ejecutan como una unidad indivisible:
o se aplican todas, o no se aplica ninguna. Las propiedades ACID describen las garantías que debe
cumplir una transacción bien implementada. Atomicidad significa que la transacción es todo o nada.
Consistencia significa que la transacción lleva a la base de datos de un estado válido a otro estado
válido, respetando todas las restricciones definidas. Aislamiento (isolation) significa que las
transacciones concurrentes no deberían interferir entre sí de forma que produzcan resultados
incorrectos, aunque el nivel exacto de aislamiento es configurable y existe un compromiso entre
aislamiento estricto y rendimiento. Durabilidad significa que, una vez confirmada (commit) una
transacción, sus cambios persisten incluso ante una caída del sistema inmediatamente después.

Bases de datos NoSQL

En las últimas dos décadas surgieron sistemas de bases de datos que no siguen el modelo relacional
estricto, agrupados bajo el término NoSQL. Entre las categorías más comunes están las bases de datos
documentales, como MongoDB, que almacenan registros como documentos JSON flexibles en lugar de filas
de esquema fijo; las bases de datos de clave-valor, como Redis, optimizadas para lecturas y
escrituras extremadamente rápidas de pares simples; las bases de datos de grafos, como Neo4j,
pensadas para modelar relaciones complejas entre entidades; y las bases de datos columnares, como
Cassandra, diseñadas para escalar horizontalmente en grandes volúmenes de escritura distribuida.

La elección entre un modelo relacional y uno NoSQL no es una cuestión de cuál es mejor en abstracto,
sino de qué tan bien se ajusta cada modelo al patrón de acceso a los datos de la aplicación concreta:
la consistencia fuerte y las relaciones estructuradas favorecen al modelo relacional, mientras que la
flexibilidad de esquema y la escalabilidad horizontal favorecen a las opciones NoSQL.
